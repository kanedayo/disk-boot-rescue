# 実案例（匿名化）

> 本ケースは実障害から抽出した。ホスト名 / IP / MAC / ディスクシリアル / パーティション GUID / ユーザーパス等はすべて除去または相対日付に置き換えている。技術的数値（サイズ・速度・オフセット・チェック数）は実測値を保持。

## 全体像

- 対象: x86_64 Linux サーバ（GPT + RAID1、2×500GB HDD、legacy BIOS + GRUB legacy i386-pc、UEFI は非標準ファームウェアで事実上機能しなかった）
- 障害: 起動不能（7 分間の再起動ループ）。`/proc/partitions` に RAID メンバーのパーティションが存在しない
- 結果: **D1 に 62.3GiB のデータ救出 → D5 に根本原因特定 + 自動修復を 1 PXE サイクルで適用 → ローカル起動回復・安定稼働**

## タイムライン

### D0 — 障害発生
- d-i（インストーラ）経由でのみ起動可能。メディア挿在時のみ動く
- 「GPT が壊れている」が初期の仮説（のちに**誤り**と判明）

### D1 — データ救出（62.3GiB）
- 救援環境から md スーパブロックを raw ダンプし、**pad3 の単一ビット反転**を発見
- 沈黙的 `-EINVAL`（§partition-parsing.md §3.2）: csum 対象外の pad が非ゼロで警告なし
- パッチ（pad ゼロ化 + csum 再計算）適用、`mdadm --examine` で別経路検証
- **18.9 分 @ 56MB/s** で全 24,565 ファイル救出（rc=0）
- 途中の偽陽性: 誤った seek オフセット（パーティション先頭からの相対値をディスク絶対値と混同）で「パッチ済み」自己整合的な読み戻しが数ラウンド続いた（§3.4）

### D2 — ブート経路の特定
- GRUB legacy (i386-pc) を **USB に配置**した暫定構成で起動確認
- NVRAM フォレンジクス: efibootmgr の表示は不整合（非標準ファームウェアの EFI 変数レイアウト）
- `BootCurrentDP` の生バイトが正しくブートした経路の唯一の確実な情報源（§partition-parsing.md §5）
- 標準 GPT HD ノードをこのファームウェアは解決しない → legacy BBS + GRUB legacy へ転換

### D3 — PXE ブリッジ
- ホストは死んでいるが LAN 到達可能 → 救援マシンから dnsmasq + TFTP のブリッジ
- dnsmasq の沈黙原因 2 つ（§pxe-bridge.md §2）: `enable_pxe` 単独では無効、vendor class は option 60
- macOS のローカルブロードキャストはローカル側 NIC に再配信されない → tcpdump で実転送確認

### D4 — 救援 initrd + GRUB legacy
- `update-initramfs`（docker）が壊れた initrd を生成 → **手組み**（§pxe-bridge.md §3）
- GRUB legacy の core を bios_grub パーティション（p5）に配置、stage1 の ks @92 = core 開始 LBA
- 合成ディスク（sparse）で同一レイアウト + 同一障害を再現、43 チェックの回帰スイートを構築

### D5 — 根本原因 + 自動修復
- **根本原因**: LBA0 のパーティション表領域（446-509）に **0xEE を含まない「有効に見える」ファクトリ MBR レコード**（2× FAT12, type 0x01）が存在
- カーネルの `msdos.c` がこのレコードを領し、GPT パーサに譲らない → GPT パーティションは**存在しない**（§partition-parsing.md §1）
- GPT テンプレート自体は**一切損傷しておらず**（当初の「GPT 破損」仮説は誤り）
- 自動修復スクリプト（repair, expect/patch + 分類 FATAL）を救援 initrd に同梱
- **1 PXE サイクルで適用**: pre-state 期待値確認 → LBA0 のテーブル領域を単一 0xEE protective にパッチ（stage1 + 55AA 保持）→ 対応する backup GPT を書込 → `O_DIRECT` readback → `reboot -f`
- ローカル起動を検証（`/proc/cmdline` がローカル由来か PXE 由来か）、複数回再起動で安定確認
- 43/43 の合成ディスク回帰テストが実適用の前提

## 教訓（10）

1. **「GPT が壊れている」と仮定する前に必ず LBA0 を見る。** 壊れているのは GPT ではなく LBA0 の「ゲート」（0xEE の有無）だった。
2. **警告のない `-EINVAL` は csum 対象外の pad を疑う。** 単一ビット反転でもアセンブル拒否。
3. **seek/skip は「相対何を」を明記。** パーティションデバイスに対する seek はパーティション先頭からの相対値。
4. **読み戻し検証は別経路 + O_DIRECT。** 書き込みと同じコマンドでの読み戻しはページキャッシュの偽陽性を検出できない。
5. **efibootmgr の表示を信用しない。** 非標準ファームウェアでは efivarfs の生バイト + `BootCurrentDP` が唯一の確実な情報源。
6. **dnsmasq の PXE は沈黙する。** `enable_pxe` 単独では無効、vendor class は option 60、tcpdump で実転送を確認。
7. **`update-initramfs` を信用しない場合がある。** 壊れた initrd を防ぐには手組み + 成果物検証 + 可能なら起動テスト。
8. **実ディスクに触る前に合成ディスクで回帰テスト。** 43 チェック + 実障害再現を含む FATAL 全分岐を通してから適用。
9. **バックアップの削除は方向性のルール。** tar にあって live に無い（missing）が 1 件でもあれば削除不可。extra（live のみ）は無関係。
10. **唯一のコピーを /tmp に置かない。証拠を削除する前に「現行が保持しているか」を確認。**
